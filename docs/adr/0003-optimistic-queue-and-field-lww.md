# 0003. 동시 편집: snapshot rebase 낙관적 업데이트와 필드 단위 last-write-wins

- 상태: 채택
- 날짜: 2026-10-17

## 배경

**공유 링크**를 가진 여러 사람이 같은 **여행**을 동시에 편집합니다. [ADR 0002](0002-share-token-rpc-and-broadcast-signal.md)에 따라 클라이언트는 Broadcast 신호를 받을 때마다 여행 전체를 다시 조회합니다. 편집 이력과 되돌리기 기능은 없습니다. 결정 과정은 [동시 편집 충돌 처리 정책](https://github.com/sunwjy/forj/issues/7)에 기록되어 있습니다.

## 결정

1. **충돌은 필드 단위 last-write-wins로 처리합니다.** 수정 RPC에는 바뀐 필드만 보내며, 시작 시각과 종료 시각은 한 묶음으로 보냅니다. 버전 검사나 충돌 감지는 하지 않습니다.
2. **삭제는 확인한 대상에만 수행합니다.** 쓰기 RPC는 여행 행을 잠근 상태에서 날짜가 기간 안에 있는지 검사합니다. 기간 변경 RPC는 사용자가 확인한 삭제 대상 id 목록을 받고, 실제 삭제 대상과 다르면 아무것도 바꾸지 않고 거부합니다.
3. **편집은 Linear 방식의 낙관적 업데이트로 즉시 반영합니다.** 화면은 서버 snapshot 위에 대기 중인 변경 queue를 다시 적용(rebase)한 결과입니다. 변경은 RPC가 성공하고, 그 이후에 요청한 snapshot이 도착했을 때 queue에서 제거됩니다. queue의 변경은 만든 순서대로 하나씩 보냅니다. 네트워크 오류가 나면 재시도하고, 서버가 거부한 변경만 되돌립니다.
4. **새 일정 항목의 id는 클라이언트가 생성합니다.** 생성 RPC는 같은 id의 재요청을 무시합니다(idempotent).

## 검토했다가 버린 선택지

- **버전 검사(optimistic concurrency)**: 몇 명의 일행이 몇 초 안에 서로의 변경을 보는 환경에서는 같은 필드를 동시에 고칠 일이 드뭅니다. 반면에 버전 검사를 도입하면 거부와 비교 UI 때문에 RPC와 화면이 모두 복잡해집니다.
- **서버 응답 후 반영**: 구현은 단순하지만, 저장할 때마다 대기 상태가 생겨서 사용 경험이 매끄럽지 않습니다.
- **항목 전체 덮어쓰기**: 서로 다른 필드를 고친 두 사람 가운데 한 사람의 수정이 사라집니다.

## 결과

- 같은 필드를 동시에 고치면 먼저 저장한 값은 아무 안내 없이 사라집니다. 편집 이력이 없으므로 이 값은 복구할 수 없습니다.
- 서버가 거부한 입력은 토스트의 「다시 편집」이나 「새 일정으로 추가」 액션으로 다시 열 수 있게 해서, 사용자가 입력한 내용을 잃지 않도록 합니다.
- queue는 메모리에만 두므로 새로고침하면 보내지 못한 변경이 사라집니다. 대신 queue가 비어 있지 않으면 탭을 닫을 때 경고합니다. 오프라인 편집을 지원하려면 queue 보존 방식을 다시 설계해야 합니다.
- 여러 사람이 함께 쓰는 일반 텍스트(예: 긴 공동 메모)를 지원하려면 필드 단위 last-write-wins로는 부족하므로, CRDT 같은 다른 모델이 필요합니다.
