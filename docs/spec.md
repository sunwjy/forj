# forj MVP 스펙

회원가입 없이 공유 링크만으로 여러 사람이 함께 보고 편집하는 여행 일정표의 MVP 스펙입니다.

- 이 문서는 "무엇을 만드는가"를 서술합니다. "왜 이렇게 했는가"는 [ADR](adr/)과 결정 티켓에 있습니다.
- 결정 과정은 [여행 플래너 MVP 스펙](https://github.com/sunwjy/forj/issues/1) map과 그 하위 티켓에 남아 있습니다. 이 문서와 티켓의 내용이 다르면 **이 문서가 기준**입니다.
- 용어는 [`GLOSSARY.md`](../GLOSSARY.md)를 따릅니다: **여행**, **일차**, **일정 항목**, **공유 링크**, **최근 여행**. 화면 문구에서는 일정 항목을 "일정"이라고 부릅니다.
- 운영 절차는 [`docs/runbook.md`](runbook.md)에 있습니다.
- 모든 문구는 초안이며, 구현하면서 다듬을 수 있습니다.

## 1. 제품 범위

- 모바일 우선 반응형 웹이며, UI는 한국어만 지원합니다.
- 회원가입과 로그인은 없습니다. 공유 링크를 가진 사람은 누구나 같은 권한으로 여행을 보고 편집합니다.
- 다른 사람의 편집은 새로고침 없이 몇 초 안에 반영됩니다.

### 1.1 MVP에서 만들지 않는 것

다음은 범위 밖입니다. "추후 후보"는 나중에 추가할 수 있도록 구조만 열어 둔 항목입니다.

- 다른 사람의 커서와 접속 상태 표시 (추후 후보)
- 보기 전용 링크, 편집 이력, 되돌리기
- 공유 링크 재발급과 폐기 (추후 후보)
- 여행 날짜 옮기기: 기간 길이를 유지한 채 모든 일정 항목을 함께 이동 (추후 후보)
- 일정 항목 종류와 교통 일정 항목의 티켓 카드 (추후 후보)
- 최근 여행의 기기 간 동기화
- 요청 rate limit, CAPTCHA, 자동 남용 감시 (추후 후보)
- 오래된 여행의 자동 정리 (추후 후보, 기준은 `end_date`)
- 공유 링크를 가진 사람의 여행 삭제 (추후 후보)
- 프로젝트 외부 저장소로의 백업 (추후 후보)
- 지도와 장소 검색, 예산 관리, 사진과 첨부 파일
- 네이티브 앱, PWA, 오프라인 편집, 다국어 UI

## 2. 도메인 규칙

### 2.1 여행

| 필드 | 규칙 |
|---|---|
| 제목 | 필수. 앞뒤 공백을 제거한 뒤 1~100자 |
| 시작일, 종료일 | 기간은 1~30일. 시작일 = 종료일을 허용하고, 종료일은 시작일보다 앞설 수 없습니다. 과거 날짜는 제한하지 않습니다 |

- 여행에는 제목과 기간 외의 필드(설명, 커버 이모지 등)를 두지 않습니다.
- 여행 하나에 일정 항목은 최대 500개입니다.
- 여행은 자동으로 삭제되지 않습니다. 사용자가 여행을 삭제하는 기능도 없습니다.

### 2.2 일차

- 일차는 여행 기간에 포함된 날짜마다 하나씩 있으며, 기간에서 계산됩니다. 날짜 외에 자체 정보를 갖지 않고, 따로 저장하지 않습니다.

### 2.3 일정 항목

| 필드 | 필수 여부 | 규칙 |
|---|---|---|
| 제목 | 필수 | 한 줄. 앞뒤 공백을 제거한 뒤 1~100자 |
| 메모 | 선택 | 여러 줄. 최대 2,000자. 공백만 있으면 비운 것으로 저장합니다 |
| 시작 시각 | 선택 | 00:00~23:59, 분 단위. 타임존 변환 없이 현지 시각 그대로 저장하고 표시합니다 |
| 종료 시각 | 선택 | 시작 시각이 있을 때만 입력할 수 있습니다 |
| 이모지 | 선택 | 이모지 한 글자(grapheme 하나). 없으면 기본 아이콘 📍를 표시합니다 |

- 일정 항목은 "n일차"가 아니라 **실제 날짜**에 속합니다.
- 장소 필드와 일정 항목 종류는 두지 않습니다. 장소는 제목이나 메모에 적습니다.
- 자정 이후에 시작하는 활동은 실제 시작 날짜의 일정 항목입니다. "25:00" 같은 표기는 허용하지 않습니다.
- 종료 시각이 시작 시각보다 이르거나 같으면 다음 날 시각으로 해석하고 "+1"을 붙여 표시합니다. 따라서 일정 항목의 길이는 24시간 미만입니다.
- 소요 시간은 저장하지 않습니다. 편집 폼에서 소요 시간을 골라 종료 시각을 채우는 편의 기능만 제공하고, 표시할 때는 두 시각으로 계산합니다.
- 길이는 code point 수로 셉니다(서버는 `char_length`, 클라이언트는 `[...str].length`).

### 2.4 정렬

- 같은 일차 안에서는 시작 시각 순서로만 자동 정렬합니다. 수동 정렬은 없습니다.
- 시작 시각이 같으면 먼저 만든 항목이 위에 옵니다.
- 시각이 없는 항목은 일차 맨 아래의 "시간 미정" 묶음에 생성 순서로 둡니다.
- 서버와 클라이언트는 같은 규칙으로 정렬합니다: `date, start_time nulls last, created_at, id`.

### 2.5 시간 겹침

- 겹치는 항목의 저장을 막지 않습니다.
- 시작 시각과 종료 시각이 모두 있는 항목끼리만 겹침을 판단하고, 편집 시트 안에서만 "14:00~15:30 ○○와 시간이 겹칩니다" 같은 안내를 보여 줍니다. 타임라인에는 표시하지 않습니다.

### 2.6 기간 변경

- 공유 링크를 가진 누구나 언제든 시작일과 종료일을 바꿀 수 있습니다.
- 기간을 바꾸면 양 끝에서 일차가 추가되거나 사라질 뿐이며, 남아 있는 날짜의 일정 항목은 그대로 유지됩니다.
- 기간을 줄여서 일정 항목이 있는 날짜가 빠지면, 빠지는 날짜와 삭제될 일정 목록을 보여 주는 확인을 받은 뒤 기간 변경과 항목 삭제를 함께 수행합니다. 되돌리기가 없으므로 이 정보는 반드시 보여 줍니다.

## 3. 공유 링크

- 여행마다 공유 링크가 하나 있으며, URL은 `/t/<token>`입니다. 루트 `/`는 첫 화면입니다.
- 토큰은 128비트 난수를 base64url로 인코딩한 22자 문자열입니다. 여행 생성 RPC 안에서 `gen_random_bytes(16)`로 만듭니다.
- 토큰은 내부 식별자(`trips.id`)와 분리되어 있으며, 외부에는 토큰만 노출합니다.
- 링크에는 만료 기한이 없고, 재발급하거나 폐기할 수 없습니다. 링크의 수명은 여행의 수명과 같습니다.
- 토큰이 128비트이므로 추측을 막는 별도의 방어(실패 횟수 제한 등)는 두지 않습니다.

## 4. 아키텍처

근거: [ADR 0002](adr/0002-share-token-rpc-and-broadcast-signal.md)

- **스택**: Next.js 단일 애플리케이션(Vercel 배포), Supabase(Postgres + Realtime).
- **데이터 경로**: 브라우저는 publishable key로 `public` schema의 `security definer` RPC만 직접 호출합니다. 테이블은 anon에게 모두 막혀 있습니다. 모든 RPC는 토큰을 인자로 받아 Postgres 안에서 검증합니다.
- **실시간 반영**: DB 트리거가 `trip:<token>` topic으로 내용 없는 public Broadcast 신호를 보내고, 클라이언트는 신호를 받으면 여행을 다시 조회합니다. `postgres_changes`, 익명 로그인, 직접 서명한 JWT는 쓰지 않습니다. 가짜 신호를 받더라도 불필요한 재조회 한 번으로 끝나므로 이 위험은 감수합니다.
- **Next.js의 역할**: 화면은 클라이언트 컴포넌트로 구성합니다. 서버에서 실행되는 부분은 메신저 링크 미리보기를 만드는 `generateMetadata` 하나이며, 이 함수도 publishable key로 `get_trip`을 호출합니다. Next.js는 secret key를 보유하지 않고 데이터 경로에 들어가지 않습니다.

## 5. 데이터베이스

### 5.1 테이블

테이블은 PostgREST에 노출되지 않는 `private` schema에 둡니다.

| 테이블 | 컬럼 |
|---|---|
| `trips` | `id uuid` PK(내부용), `share_token text unique`, `title`, `start_date date`, `end_date date`, `created_at` |
| `items` | `id uuid` PK(클라이언트 생성), `trip_id` FK `on delete cascade`, `date date`, `title`, `memo`(nullable), `start_time time`(nullable), `end_time time`(nullable), `emoji`(nullable), `created_at` |
| `app_settings` | 한 행만 둡니다. `trip_creation_enabled boolean` |

- DB에는 PK, FK, `not null`, `unique`만 둡니다. 값 검증은 모두 RPC에서 수행합니다. 따라서 운영자가 SQL로 직접 수정하면 이 검증은 적용되지 않습니다.
- `last_accessed_at` 같은 접근 기록은 두지 않습니다.
- `app_settings`의 유일한 행(`trip_creation_enabled = true`)은 마이그레이션에서 insert합니다.

### 5.2 권한

- 모든 RPC는 `public` schema의 `security definer` 함수입니다. 함수마다 `set search_path = ''`를 지정하고, 함수 안에서는 모든 이름을 schema까지 붙여서 씁니다.
- RPC의 실행 권한은 `public`에서 회수한 뒤 `anon`에게만 부여합니다.
- `private` schema의 `usage` 권한은 `anon`과 `authenticated`에게 주지 않습니다.

### 5.3 RPC

| RPC | 동작 |
|---|---|
| `create_trip(title, start_date, end_date)` | 차단 스위치와 입력값을 검사하고 토큰을 만듭니다. **토큰만** 돌려줍니다 |
| `get_trip(token)` | snapshot을 돌려줍니다(아래 참고) |
| `update_trip_title(token, title)` | 여행 제목을 바꿉니다 |
| `set_trip_dates(token, start_date, end_date, confirmed_deleted_ids uuid[])` | 여행 행을 잠근 상태에서 기간을 바꾸고 범위 밖 항목을 삭제합니다. 실제 삭제 대상이 확인 목록과 집합으로서 다르면 아무것도 바꾸지 않고 `DELETION_MISMATCH`로 거부합니다 |
| `create_item(token, id, date, title, memo, start_time, end_time, emoji)` | 여행 행을 잠근 상태에서 기간과 500개 상한을 검사합니다. 같은 여행에 같은 id가 이미 있으면 내용을 비교하지 않고 성공으로 처리합니다(idempotent). 다른 여행에 같은 id가 있으면 `INVALID_INPUT`으로 거부합니다 |
| `update_item(token, item_id, patch jsonb)` | key가 있는 필드만 반영하고, 값이 `null`이면 그 필드를 비웁니다. `start_time`과 `end_time`은 둘 다 오거나 둘 다 오지 않아야 합니다. patch에 `date`가 있으면 여행 행을 잠근 상태에서 기간을 검사합니다 |
| `delete_item(token, item_id)` | 이미 없는 항목을 받아도 성공으로 처리합니다 |

`get_trip` snapshot은 내부 `trips.id`를 노출하지 않으며, `items`는 [2.4](#24-정렬)의 순서로 정렬되어 있습니다.

```json
{ "title": "...", "start_date": "2026-11-20", "end_date": "2026-11-23",
  "items": [{ "id": "...", "date": "...", "title": "...", "memo": null,
              "start_time": "09:00", "end_time": null, "emoji": null, "created_at": "..." }] }
```

### 5.4 검증과 정규화

- 상한은 [2장](#2-도메인-규칙)의 수치를 따르며, 이모지는 16 code point 이하입니다. 상한은 RPC 안의 상수로 두므로 함수만 다시 정의하면 바꿀 수 있습니다.
- 시각은 초 값이 0이어야 하고, `end_time`은 `start_time`이 있을 때만 허용합니다.
- 제목은 앞뒤 공백을 제거해 저장합니다. 메모는 비어 있거나 공백만 있으면 `null`로 저장합니다. 저장되는 값은 서버에서 정규화한 결과입니다.
- 이모지가 grapheme 하나인지는 클라이언트에서만 `Intl.Segmenter`로 검사합니다. 서버는 비어 있지 않은지와 길이 상한만 검사합니다.

### 5.5 오류 코드

`raise exception`의 `message`에 아래 코드를 넣고, `errcode`는 기본값 `P0001`을 씁니다. 사람이 읽는 설명은 `detail`에 넣고, `INVALID_INPUT`이면 `detail`에 필드 이름을 넣습니다.

| 코드 | 상황 |
|---|---|
| `TRIP_NOT_FOUND` | 토큰에 해당하는 여행이 없음. 모든 RPC가 이 코드를 내며, `get_trip`도 `null`을 돌려주지 않습니다 |
| `ITEM_NOT_FOUND` | 수정 대상 일정 항목이 없음 |
| `DATE_OUT_OF_RANGE` | 일정 항목의 날짜가 여행 기간 밖임 |
| `DELETION_MISMATCH` | 기간 변경 시 확인한 삭제 대상과 실제 삭제 대상이 다름 |
| `INVALID_PERIOD` | 기간이 1~30일이 아니거나 종료일이 시작일보다 앞섬 |
| `ITEM_LIMIT_REACHED` | 여행의 일정 항목이 500개에 도달함 |
| `TRIP_CREATION_DISABLED` | 여행 생성 차단 스위치가 꺼져 있음 |
| `INVALID_INPUT` | 그 밖의 입력값 검증 실패 |

### 5.6 변경 신호

- `trips`와 `items`에 statement-level `AFTER` 트리거(`INSERT`, `UPDATE`, `DELETE`)를 겁니다. 트리거는 transition table에서 영향받은 여행을 모으고, 여행마다 `realtime.send('{}', 'changed', 'trip:<token>', false)`를 한 번씩 호출합니다.
- payload는 비워 두고 보낸 사람 정보도 넣지 않습니다. 보낸 사람도 snapshot을 다시 받아야 queue를 비울 수 있기 때문입니다.
- `trips`의 `DELETE`에서는 `OLD` transition table의 토큰으로 신호를 보냅니다. cascade로 함께 지워지는 `items`의 트리거는 여행의 토큰을 찾을 수 없으므로 그 여행을 건너뜁니다.
- `set_trip_dates`처럼 두 테이블을 건드리는 RPC는 신호를 두 번 보냅니다. 클라이언트가 몰린 신호를 합치므로 문제가 되지 않습니다.

## 6. 동시 편집과 낙관적 업데이트

근거: [ADR 0003](adr/0003-optimistic-queue-and-field-lww.md)

### 6.1 충돌 모델

- 수정할 때는 편집 시트를 열었을 때와 비교해 **바뀐 필드만** 보냅니다. 시작 시각과 종료 시각은 둘 중 하나라도 바뀌면 한 묶음으로 보냅니다.
- 같은 필드를 동시에 고치면 **필드 단위 last-write-wins**로 처리합니다. 버전 검사와 충돌 감지는 하지 않습니다.
- 일정 항목을 추가하거나 날짜를 옮기는 쓰기는 여행 행을 잠근 상태에서 기간을 검사하므로, 기간 축소와 경합해도 기간 밖 항목이 남지 않습니다.
- 기간 변경은 사용자가 확인한 삭제 대상 id 목록을 함께 보내므로, 확인하지 않은 항목은 삭제되지 않습니다.

### 6.2 로컬 상태

- 로컬 상태는 **서버 snapshot**과 **대기 중인 변경 queue**로 구성합니다. 화면에는 snapshot 위에 queue를 순서대로 다시 적용(rebase)한 결과를 그립니다.
- 변경은 RPC가 성공하고, 그 이후에 요청한 snapshot이 도착했을 때 queue에서 제거됩니다.
- 새 일정 항목의 id는 클라이언트가 uuid로 생성합니다.

### 6.3 전송 규칙

- queue의 변경은 만든 순서대로 하나씩 보냅니다.
- 네트워크 오류나 timeout이 발생하면 변경을 되돌리지 않고, 간격을 늘려 가며 재시도합니다.
- 평소에는 저장 중 표시를 하지 않습니다. 몇 초 이상 전송하지 못하면 연결 끊김 표시를 보여 줍니다([7.7](#77-동시-편집-상태-표시)).
- queue가 비어 있지 않은 상태에서 탭을 닫으려 하면 `beforeunload` 경고를 띄웁니다.
- queue는 새로고침 이후까지 보존하지 않습니다.

### 6.4 재조회

- `changed` 신호를 받거나, 채널에 다시 연결되거나, 탭이 다시 보이거나(`visibilitychange`), 네트워크가 복구되면 여행을 다시 조회합니다.
- 짧은 시간에 몰린 신호는 재조회 한 번으로 합칩니다. 가장 최근 요청의 응답만 반영하고, polling은 하지 않습니다.

### 6.5 거부된 변경

서버가 거부한 변경은 queue에서 제거해 화면에서 되돌리고 안내합니다.

| 상황 | 처리 |
|---|---|
| 편집 시트를 연 상태에서 재조회 결과로 항목이 삭제된 사실을 알게 됨 | 시트 위쪽에 「삭제된 일정입니다」 배너와 「새 일정으로 추가」·「닫기」 버튼을 보여 줍니다 |
| 시트를 닫은 뒤 수정이 `ITEM_NOT_FOUND`로 거부됨 | 토스트 「삭제된 일정이라 저장하지 못했어요」와 「새 일정으로 추가」 액션(입력값을 담은 시트를 다시 엶) |
| 추가하거나 날짜를 옮긴 항목이 `DATE_OUT_OF_RANGE`로 거부됨 | 낙관적으로 그린 항목이 사라지고, 토스트 「여행 기간에서 빠진 날짜예요」와 「다시 편집」 액션 |
| 기간 변경이 `DELETION_MISMATCH`로 거부됨 | 기간을 원래대로 되돌리고, 최신 삭제 대상으로 확인 대화상자를 다시 띄웁니다 |
| `ITEM_LIMIT_REACHED`, `INVALID_INPUT` 등 그 밖의 거부 | 변경을 되돌리고 토스트 「저장하지 못했어요」. 일정이 남아 있으면 「다시 편집」 액션을 둡니다 |
| `TRIP_NOT_FOUND` | queue를 버리고 [여행을 찾을 수 없음](#76-여행을-찾을-수-없음) 화면으로 바꿉니다 |

## 7. 화면

모든 화면은 시트형으로 구성합니다. 추가·편집은 바텀시트에서 하고, 「저장」을 눌러야 반영됩니다. 참고 프로토타입: [`prototype/core-screens`](https://github.com/sunwjy/forj/tree/prototype/core-screens/prototypes/core-screens) 브랜치의 A 시안(공유 버튼 모양만 다릅니다).

### 7.1 첫 화면 `/`

- 최근 여행이 없으면 소개 문구 아래에 여행 만들기 폼(제목, 시작일, 종료일)을 바로 보여 줍니다.
- 최근 여행이 있으면 「＋ 새 여행 만들기」 주 버튼 아래에 최근 여행을 보여 줍니다. 버튼을 누르면 같은 폼이 바텀시트로 열립니다.
- 여행을 만들면 `/t/<token>`으로 이동하고, 공유 아이콘으로 링크를 보낼 수 있다는 토스트를 띄웁니다. 별도의 배너나 안내 시트는 두지 않습니다.
- 생성이 `TRIP_CREATION_DISABLED`로 거부되면 폼을 유지한 채 "지금은 여행을 만들 수 없습니다. 잠시 후 다시 시도해 주세요."라고 안내합니다.

### 7.2 최근 여행

- 이 브라우저의 `localStorage`에 저장합니다. 항목마다 토큰, 여행 제목, 시작일, 종료일의 snapshot과 마지막으로 연 시각을 둡니다.
- 여행을 만들었을 때, 그리고 여행 화면에서 조회에 성공할 때마다 추가하거나 갱신합니다. 공유받아 열어 본 여행도 포함합니다.
- 마지막으로 연 시각 기준으로 최근 순서로 정렬하고, 최대 50개까지 보관합니다. 넘치면 가장 오래된 항목부터 밀어냅니다.
- 첫 화면은 네트워크 요청 없이 snapshot만으로 그립니다. 내가 다시 열기 전까지 예전 제목이 보이는 것은 허용합니다.
- 각 행의 × 버튼은 「목록에서 지우기」입니다. 여행은 삭제하지 않으며, 확인 대화상자 대신 「되돌리기」 액션이 있는 토스트를 띄웁니다.
- 조회 결과가 `TRIP_NOT_FOUND`이면 그 항목을 목록에서 자동으로 지웁니다. 네트워크 오류일 때는 지우지 않습니다.

### 7.3 여행 화면 `/t/<token>`

위에서 아래로 다음과 같이 구성합니다.

1. 상단 바: 뒤로, D-day, 공유 아이콘
2. 여행 제목과 기간, 제목 옆 ✏️(여행 정보 수정)
3. 일차 칩
4. 타임라인: 시작 시각 순서로 일정 카드를 놓고, 맨 아래에 "시간 미정" 묶음을 둡니다
5. 플로팅 「＋ 일정 추가」 버튼

### 7.4 일정 추가와 편집

- 카드나 플로팅 버튼을 누르면 바텀시트가 열립니다. 필드는 이모지, 제목, 일차, 시작·종료 시각, 메모입니다.
- 이모지는 자주 쓰는 여행 이모지 10여 개의 추천 목록과 휴대폰 이모지 키보드 입력을 함께 제공합니다.
- 「저장」을 누르면 저장 중 표시 없이 낙관적으로 반영합니다.
- 기존 일정에는 「삭제」가 있으며, 확인 대화상자를 거칩니다.
- 시간이 겹치면 시트 안에서만 안내합니다([2.5](#25-시간-겹침)).

### 7.5 여행 정보 수정과 공유

- 제목 옆 ✏️를 누르면 제목, 시작일, 종료일을 고치는 바텀시트가 열립니다. 기간을 줄여 일정이 빠지면 빠지는 날짜와 삭제될 일정 목록을 보여 주는 확인 대화상자를 띄웁니다.
- 상단 바의 공유 아이콘을 누르면 공유 링크를 복사하고 "공유 링크를 복사했어요" 토스트를 띄웁니다.
- 메신저 링크 미리보기: `generateMetadata`가 `get_trip`을 호출해 여행 제목과 기간을 미리보기에 넣습니다. `TRIP_NOT_FOUND`이면 404로 처리합니다.

### 7.6 여행을 찾을 수 없음

- 안내 문구("링크가 정확한지 확인해 주세요. 여행이 삭제되었을 수도 있어요.")와 「처음 화면으로」 버튼만 둡니다.
- 처음 링크를 열었을 때와 열려 있는 도중에 `TRIP_NOT_FOUND`를 받은 경우를 구분하지 않고 같은 화면으로 처리합니다. 이때 queue를 버리고, 최근 여행에서 그 여행을 뺍니다.

### 7.7 동시 편집 상태 표시

- 연결이 끊기면 상단 바의 D-day 자리에 "연결 끊김 · 다시 연결하는 중"을 표시하고, 편집 시트 위쪽에도 같은 표시를 보여 줍니다.
- 편집 시트를 연 동안 다른 사람이 필드를 바꾸면 그 필드를 버터색으로 하이라이트합니다.
  - 내가 건드리지 않은 필드는 새 값으로 바꾸고 "방금 다른 사람이 바꿨어요"라고 표시합니다.
  - 내가 고친 필드는 내 입력을 유지하고 "저장하면 내 입력으로 바뀌어요"라고 안내합니다.

### 7.8 시각 디자인

- [ADR 0001](adr/0001-visual-direction-ticket-timeline-peach.md)과 [시각 디자인 명세](design/visual-design.md)를 따릅니다: 왼쪽 정렬 타임라인, 크림 배경과 복숭아 강조색.
- 모든 일정 항목은 일반 카드로 그립니다. 명세의 티켓 카드(4.6)와 공유 링크 배너(4.7)는 쓰지 않습니다.
- MVP는 라이트 모드만 지원합니다. 다크 모드 토큰은 검증되지 않은 초안이므로 적용하지 않습니다.

## 8. 남용 방지

- 실수나 단순 스크립트로 생기는 폭주만 막습니다. 의도적인 공격은 MVP 범위 밖입니다.
- 여행 크기 상한([2장](#2-도메인-규칙))을 RPC 검증으로 강제합니다.
- 여행 생성과 일정 항목 생성에 전역 상한이나 IP별 제한을 두지 않습니다. 조회와 수정의 부하는 Supabase 플랫폼 수준의 보호에 맡깁니다.
- `app_settings.trip_creation_enabled`를 끄면 배포 없이 여행 생성을 즉시 막을 수 있습니다. 남용은 운영자가 발견했을 때 사후에 대응합니다([runbook](runbook.md)).

## 9. 개발과 배포

### 9.1 환경

- 로컬 Supabase(`supabase start`)와 운영 Supabase 프로젝트 하나로 구성합니다. staging 프로젝트와 Supabase Branching은 두지 않습니다.
- Vercel preview 배포는 두지 않습니다. `vercel.json`에서 `git.deploymentEnabled: false`로 Git 자동 배포를 끕니다.
- 리전: Supabase는 Seoul(`ap-northeast-2`), `generateMetadata`가 실행되는 Vercel Function은 `icn1`입니다.
- 운영 프로젝트는 무료 플랜을 유지합니다.

### 9.2 마이그레이션

- `supabase migration new`로 만든 명령형 SQL 파일(`supabase/migrations/`)로 관리합니다. 선언형 스키마와 `db diff`는 쓰지 않습니다.
- 함수를 바꿀 때는 `create or replace function` 전체를 새 파일에 씁니다.
- 마이그레이션은 직전에 배포된 프론트엔드와 호환되어야 합니다. RPC 시그니처를 바꿀 때는 새 함수를 추가하고, 기존 함수는 다음 배포에서 제거합니다.
- 개발용 예시 여행은 고정 토큰으로 `supabase/seed.sql`에 둡니다.

### 9.3 CI

- PR마다 lint, typecheck, `next build`, Vitest 단위 테스트, pgTAP 테스트를 실행하고, 모두 통과해야 merge할 수 있습니다.
- pgTAP 테스트는 `supabase/tests/`에 두고 `supabase start` → `supabase db reset` → `supabase test db` 순서로 실행합니다. anon이 `private` schema에 직접 접근할 수 없다는 점과, RPC가 정해진 오류 코드를 내는 점을 검증합니다.
- Vitest는 DB 밖의 순수 로직(queue rebase, 바뀐 필드 계산, 정렬과 "시간 미정" 분류, 최근 여행 목록 관리, 입력 검증)을 검증합니다. E2E 테스트는 두지 않습니다.

### 9.4 배포

- `main`에 push되면 GitHub Actions가 `supabase db push`를 실행하고, 성공한 경우에만 Vercel Deploy Hook을 호출합니다.

### 9.5 환경 변수와 secret

- **Vercel**: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 두 개만 대시보드에 직접 등록합니다. Vercel Marketplace의 Supabase 연동은 쓰지 않습니다.
- **로컬**: `.env.example`을 commit하고, 실제 값은 `.env.local`에 둡니다.
- **GitHub secret**: Supabase access token, DB 비밀번호, Vercel Deploy Hook URL, Supabase Storage S3 access key, 백업 passphrase.
- secret key(service role)는 어디에도 두지 않습니다.

### 9.6 daily workflow

하나의 scheduled workflow가 매일 한 번 다음 작업을 차례로 실행합니다.

1. **keepalive**: publishable key로 존재하지 않는 고정 토큰을 넣어 `get_trip`을 호출합니다. 결과는 `TRIP_NOT_FOUND`이지만 DB 활동으로 집계되어 무료 플랜의 일시 정지를 막습니다.
2. **백업**: `supabase db dump`(스키마)와 `supabase db dump --data-only`(데이터)를 `gpg --symmetric`으로 암호화해 같은 프로젝트의 비공개 Storage bucket에 올리고, 30일보다 오래된 백업을 삭제합니다.

- dump에는 모든 공유 토큰이 들어 있으므로 Actions artifact나 로그에 절대 남기지 않습니다.
- 이 백업은 논리적 유실에만 대비합니다. 프로젝트 자체가 사라지면 백업도 함께 사라집니다.
- 복구 절차는 [runbook](runbook.md)에 있습니다.
